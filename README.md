
# AudioSync

AudioSync is a student project for sharing one local audio session with
multiple non-Apple devices. The host enables a Wi-Fi hotspot; listeners join
that network and play the host audio through their own wired or Bluetooth
headphones.

The first implementation target is a **Windows host with Android listeners**.
The user interface is built with Flutter, while the timing, packet and audio
engine is being built as a platform-neutral Rust core. Apple devices are out
of scope for this project.

## Current milestone

The repository currently contains:

- A Rust workspace with versioned audio packet primitives.
- An NTP-style clock-offset estimator.
- A bounded, reorder-aware jitter buffer.
- A fixed 48 kHz mono Opus codec boundary with packet-loss concealment.
- A PCM source and Opus encoding pipeline with a deterministic synthetic source.
- A Windows WASAPI shared-mode loopback capture adapter that converts system
  output to the codec's PCM contract.
- A Windows-only `wasapi_capture_smoke` example that round-trips live loopback
  frames through Opus without writing recordings to disk.
- A platform-neutral `AudioPacketPump` that adds sequence numbers and timestamps
  to encoded audio frames.
- A local UDP transport and host/listener session state machine.
- A UDP audio fan-out helper that sends one packet to multiple listener
  endpoints while isolating individual send failures.
- A local `audiosync-runtime` host orchestrator and reusable listener audio
  pipeline for join, approval, clock sync, jitter buffering, decoding, and
  packet-loss concealment.
- An offline host/listener simulator.
- A Flutter host/listener UI skeleton using mock session state, including mock
  host approval/removal and listener delay/volume controls.

The WASAPI adapter and capture smoke example have completed three 500-frame
native Windows smoke runs using laptop speakers, wired headphones, and a
Bluetooth headset. All three runs captured, encoded, and decoded 500 frames
with no WASAPI timeouts. The exact Windows version and hardware make/model
remain unrecorded. Android foreground playback and the Flutter engine bridge
remain future integration milestones. See
`backend/native/audio/WINDOWS_WASAPI_TESTING.md` for the Windows setup,
regression checks, live-capture command, and hardware test record.
The implementation boundary for each audio/network phase is recorded in
`IMPLEMENTATION_PHASES.md`.

## Prerequisites

### Rust core

The pinned Rust toolchain is `1.99.1`. Use a local Rust installation or the
Docker workflow below. The Opus crate builds its vendored native library through
CMake and a C compiler; the Dockerfile installs those build tools. The project
keeps `Cargo.lock` committed.

### Flutter UI

The pinned Flutter SDK is `3.47.8`, recorded in `.fvmrc`. The Android and
Windows platform directories are checked in, generated by
`flutter create --platforms=android,windows .`:

```bash
cd frontend/flutter-app
flutter pub get
```

## Run the Rust simulator

With Rust 1.99.1 available:

```bash
cargo run -p audiosync-sim --locked
```

Expected output includes:

```text
AudioSync simulator PASS
```

## Run the host and listener prototypes

Two command-line binaries stream real audio end-to-end over UDP. On Windows
the host captures system audio through WASAPI loopback; on other platforms it
falls back to a synthetic tone.

Start the host on the streaming machine:

```bash
make host                          # Windows: WASAPI capture
make host ARGS="--synthetic"       # any platform: synthetic tone
```

The host prints a ready-to-paste listener command with its session and token.
Run it on the receiving machine (add `--null-output` to skip audio playback):

```bash
make listener ARGS="--host 192.168.137.1:41000 --session <hex> --token <hex>"
```

Listener flags: `--delay-ms` (manual calibration), `--buffer-ms` (jitter
pre-roll, default 100), `--grace-ms` (loss patience), `--volume 0.0-1.0`,
`--duration-secs N`, `--csv FILE` (per-second soak metrics). The listener
prints per-second metrics (rendered and concealed frames, duplicates, late
packets, unauthenticated drops, buffer depth, clock RTT/offset). Host stdin
commands: `list` and `end`.

To calibrate two listeners against each other, record the same 30+ seconds of
playback next to each listener's headphones as 16-bit WAV and run:

```bash
make calibrate ARGS="--a listener1.wav --b listener2.wav"
```

It reports which listener leads and the `--delay-ms` adjustment that aligns
them. For the first real hotspot experiment, follow
`HOTSPOT_VALIDATION.md`.

For the first real hotspot experiment (Phase 6), run the host on the Windows
machine with its Mobile Hotspot enabled, allow the UDP port through the
firewall, and point the listener at the hotspot-side host address.

## Run the Flutter prototype

```bash
cd frontend/flutter-app
flutter pub get
flutter run -d windows
```

The UI drives the real Rust engine when `audiosync_ffi.dll` is built
(`cargo build -p audiosync-ffi --release`) and falls back to mock session
state otherwise — see `lib/engine/README.md`. Real platform audio output
(playing captured PCM on the listener device) is the next integration
milestone.

## Tests and checks

The default test command is:

```bash
make test
```

This runs the Rust test suite and the Flutter widget tests. It fails clearly if
Flutter is missing rather than reporting an incomplete test run as success.
When Flutter is unavailable, run the available core checks with:

```bash
make test-core
```

Additional checks:

```bash
make format-check
make lint
make build
make test-landing
make lint-landing
make build-landing
```

Hardware validation is separate from automated tests and requires a Windows
machine, Android devices, a host hotspot and real audio outputs.

For the current Windows WASAPI setup and testing plan, see
`backend/native/audio/WINDOWS_WASAPI_TESTING.md`.

## Docker

The Docker image provides a reproducible Rust-core test and simulator path:

```bash
docker build -t audiosync:dev .
docker run --rm audiosync:dev
```

The Windows WASAPI and Android Bluetooth paths require their target platforms
and cannot be validated by the Linux simulator container alone.

Use FVM or an equivalent SDK manager to make the version in `.fvmrc` active
before running Flutter commands. The Makefile also accepts
`FLUTTER=/path/to/flutter` when a direct SDK path is preferred.

## Development sequence

1. Keep the protocol, session, and timing behavior tested in the offline simulator.
2. Keep the synthetic PCM-to-Opus pipeline covered by the offline simulator.
3. Validate Windows WASAPI loopback capture on the target host hardware.
4. Validate the local host runtime and listener pipeline over the Windows hotspot.
5. Add the Android foreground listener service and real wired/Bluetooth playback.
6. Validate synchronization and manual per-listener delay adjustment.
7. Replace the Flutter mock session with the real engine bridge.

See `PRD.md` for product requirements and acceptance criteria.

## Run the landing page

The landing page is a Vite/TanStack application. It supports npm and Bun:

```bash
cd frontend/landing-page
npm install --legacy-peer-deps
npm run dev
```

Then open the URL printed by Vite, normally
[http://localhost:5173](http://localhost:5173).

Alternatively, use Bun with `bun install --frozen-lockfile` and `bun run dev`.
Do not open `frontend/landing-page/code.html`; that file is not part of the current
application.
